# Story 2.2: Restore & Test Contact Import Flow

## Story Goal

Implement comprehensive testing and validation of the complete CSV import flow with column mapping, including validation, error handling, and notification system. Ensure all contact import functionality works end-to-end with proper test coverage (>80%).

**Why:** Story 2.1 added the database schema for mapping persistence. Now we need to verify the entire import pipeline works correctly - from CSV upload through contact creation - with robust error handling and comprehensive test coverage.

---

## Story Description

### Problem Statement

The contact import system has advanced mapping capabilities in the frontend and backend, but lacks comprehensive test coverage. Without proper tests, we cannot be confident that:

1. CSV files are parsed correctly with column mapping
2. Phone numbers are formatted consistently
3. Email validation works properly
4. Duplicate detection prevents data corruption
5. Error handling is graceful for invalid data
6. Performance is acceptable for large files
7. No regressions exist in existing functionality

### System Context

**Related Components:**
- Model: `app/models/data_import.rb` (tracking import operations)
- Job: `app/jobs/data_import_job.rb` (async CSV processing)
- Service: `app/services/data_import/contact_manager.rb` (business logic)
- Controller: `app/controllers/api/v1/accounts/contacts_controller.rb` (API endpoint)
- Frontend: `ContactImportDialog.vue`, `ContactImportMapper.vue` (UI)
- Database: `data_imports` table (with mapping column from Story 2.1)

**Technology Stack:**
- Backend: Rails 7.0, ActiveJob with Sidekiq
- Frontend: Vue 3, Composition API
- Testing: RSpec, Factory Bot, VCR (for external API mocking)
- Database: PostgreSQL 12+

**Current State:**
- ✅ Database migration complete (Story 2.1)
- ✅ Backend code for CSV processing exists (not fully tested)
- ✅ Frontend mapping UI exists
- ❌ No comprehensive test suite
- ❌ Test coverage unknown (likely < 50%)
- ❌ Some edge cases untested

## Test Scenarios

### Scenario 1: Valid CSV with All Columns Mapped
```
Input: CSV with email, name, phone, custom fields all present
Mapping: All fields mapped correctly
Expected: All contacts created successfully, no errors
```

### Scenario 2: CSV with Missing Required Fields
```
Input: CSV with some rows missing email AND phone
Expected: Rows rejected with error "Email or Phone required"
Result: Other valid rows processed, failed rows logged
```

### Scenario 3: Invalid Phone Numbers
```
Input: CSV with invalid phone formats (abc123, 999, etc)
Expected: Phone field rejected, other fields processed
Result: Contact created without phone OR rejected entirely (depends on email)
```

### Scenario 4: Duplicate Emails
```
Input: CSV with duplicate email addresses within same file
Expected: First occurrence created, duplicates rejected
Result: No duplicate contacts in database
```

### Scenario 5: Invalid Email Format
```
Input: CSV with malformed emails (missing @, invalid domain)
Expected: Row rejected with error message
Result: Invalid row in failed records
```

### Scenario 6: Large File (1000+ rows) Performance
```
Input: CSV with 1000+ rows, all valid
Expected: Import completes in < 5 minutes
Result: All contacts created, no timeouts or memory issues
```

### Scenario 7: Mapping with Empty Columns
```
Input: CSV with empty source columns in mapping
Expected: Empty columns are skipped (not created)
Result: Contacts created without empty fields
```

### Scenario 8: Phone Number Variations
```
Input: Phones with/without +, with spaces, dashes, parentheses
Examples: 
  - 11987654321 (Brazilian)
  - +5511987654321 (with country code)
  - (11) 9 8765-4321 (formatted)
Expected: All normalized to consistent format
Result: Consistent phone format in database
```
