# Story 2.3: Enhanced Phone Formatting & WhatsApp Validation

## Story Goal

Implement robust phone number formatting and validation service that normalizes diverse phone formats (with/without country codes, spaces, dashes, parentheses) into standardized E.164 format with WhatsApp compatibility. Ensure consistent phone handling across contact import, creation, and API operations.

**Why:** Story 2.2 added comprehensive test coverage for the import flow. Now we need to implement the phone formatting logic that these tests validate - converting raw user input (11987654321, +5511987654321, (11) 9 8765-4321) into consistent E.164 format (+5511987654321) with WhatsApp validation.

---

## Story Description

### Problem Statement

The contact import system receives phone numbers in multiple formats:
1. Without country code: `11987654321` (Brazilian)
2. With country code: `+5511987654321` (international)
3. With formatting: `(11) 9 8765-4321` (user-friendly)
4. With spaces/dashes: `+55 11 9 8765-4321` (mixed)

Without standardized formatting:
- Duplicate detection fails (same number in different formats = different values)
- WhatsApp integration breaks (needs consistent E.164)
- Search/matching doesn't work across formats
- International support is brittle
- Phone field becomes unreliable for identification

### System Context

**Related Components:**
- Service: `app/services/data_import/contact_manager.rb` (uses formatter)
- Service: `app/services/phone_formatter.rb` (NEW - to create)
- Model: `app/models/contact.rb` (phone field validation)
- Job: `app/jobs/data_import_job.rb` (calls formatter)
- Controller: `app/controllers/api/v1/accounts/contacts_controller.rb` (API endpoint)
- Validator: `app/validators/phone_validator.rb` (NEW - optional)

**Technology Stack:**
- Backend: Rails 7.0
- Phone validation: `phonelib` gem (phonetic analysis library)
- Standard: E.164 format (ITU-T recommendation)
- Locale: Primary support for Brazil (+55)

**Current State:**
- ❌ No centralized phone formatter service
- ❌ Phone validation scattered across models
- ⚠️ Duplicate detection doesn't account for format variations
- ❌ WhatsApp integration not validated
- ❌ No international number support documented

## Acceptance Criteria

### Phone Formatting

- [x] **E.164 Standard:** All valid phones formatted to `+[country_code][number]`
- [x] **Brazilian Numbers:** Input like `11987654321` → `+5511987654321`
- [x] **With Country Code:** Input like `+5511987654321` → unchanged
- [x] **Formatted Input:** Input like `(11) 9 8765-4321` → `+5511987654321`
- [x] **International Support:** Accept country codes beyond Brazil (+1, +44, +81, etc)
- [x] **Strip All Formatting:** Remove spaces, dashes, parentheses, dots

### WhatsApp Validation

- [x] **WhatsApp Format Check:** Valid E.164 format is WhatsApp-compatible
- [x] **Reject Invalid Lengths:** Too short/long numbers rejected with error
- [x] **Clear Error Messages:** Include original value in error: `"Invalid phone: 999 (too short)"`

### Integration with Existing Code

- [x] **ContactManager Integration:** Phone formatter called in `build_contact` method
- [x] **Backward Compatibility:** Existing contact.phone field still works
- [x] **Duplicate Detection:** Phone duplicates detected across format variations
- [x] **Error Propagation:** Invalid phones generate clear errors to user

### Edge Cases

- [x] **Empty/Nil Phones:** Handle gracefully (optional field)
- [x] **Mixed Formats:** Same CSV with different formats handled consistently
- [x] **Unicode Digits:** Non-ASCII digits converted to ASCII
- [x] **Plus Sign Variations:** `+55`, `0055`, `55` prefix handling
- [x] **Leading Zeros:** Brazilian numbers with leading zero handled

### Testing

- [x] **Unit Tests:** PhoneFormatter service tests (20+ cases)
- [x] **Integration Tests:** ContactManager + PhoneFormatter integration
- [x] **Edge Case Tests:** Invalid formats, international numbers, edge cases
